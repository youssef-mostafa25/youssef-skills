If you have been asked to work on a task from this board, this page is the job — not the code change. You investigate one task, write a proposal in the shape below, update that task's row, and come back for approval before touching any implementation file.

The rule

No implementation before an approved plan. One task at a time. Read the task, read the code it cites, write the proposal, set the row to Plan submitted, and stop. Approval is the user saying so, in words — a silence, a thumbs-up on something else, or your own confidence that the fix is obvious are not approval.

Two things you may do without asking, because they are how the proposal gets written: read anything, and run read-only checks — greps, a throwaway probe in a scratch directory, a test suite that already exists. What you may not do is edit a file the fix would touch, or leave a scratch file behind in the repo.

If the task turns out to be wrong, say that instead of proposing a fix. A proposal that opens "this does not hold, here is why" is a good outcome and finishes the task — set the row to Refuted or By design with the evidence.

"Low risk" on a migration or a shared path.
7LegacyName it, price it, recommend — then ask.(1) What legacy logic is in reach: the old shape, name, column, route or code path, and where it is read or written. There is no default either way.Removing the old path because it looks dead. Quietly adding a fallback or a shim and not declaring it. "Not sure" — you read the file, so you know.

Legacy is the user's decision, not yours

There is no default. Do not assume the old path is removed, and do not assume it is kept. Heading 7 states what the legacy logic is, what is lost without it, and which way you would go — and then stops and asks. Nothing is implemented on that point until the answer arrives in words.

Check the lane before you plan

Name every directory this job's fixes reach. Before editing anything outside the lane you were given, ask once per job, naming every directory. Do not implement across the boundary because the fix is small — small is not the criterion.

Plan against the code, not against the row

Rows carry the evidence of the pass that wrote them, and the tree moves. Re-read the cited files before you write anything. Where what you find disagrees with the row, the code wins and the row gets corrected — that correction is part of the deliverable, not an aside.

Update the board in the same turn as the change

A status is only useful if it is true right now, so the row moves when the thing happens — not at the end of a batch and not "once it is all done". Every move updates three things together: the pill, the Evidence cell (what you did and what proved it), and the tally and chip counts in the header, which are hand-maintained and will silently disagree with the rows if you skip them.

The Queue is maintained too: a task that reaches Fixed leaves it and the ranks close up. If fixing one task changes another's priority, say so and re-rank rather than leaving a stale order behind.

Work lands uncommitted. No commit, push or PR unless the user says so, in words. Republish to the same URL so the link keeps working.
