If you have been asked to work on this board, this page is the work — not the code change. You take the next task, job or PR from the Jobs tab — whichever the user asked for — write a proposal for each of its tasks in the shape below, update their rows, and come back for approval before touching any implementation file. Every question was asked and answered before this board was published, so every task here is ready: approval is all it still needs.

The rule

No implementation before an approved plan. Plan what the user asked for: next task is one task, next job one job, next PR every job in that PR. Read the tasks, read the code they cite, write the job header and one proposal per task, set the rows to Plan submitted, and stop.

The user's preferences come first. Read ~/.claude/youssef-skills/preferences.md before anything else. It says whether you wait for approval (approval), when you stop for review (review), and whether you commit or push (commit, push). A key that is missing is asked once and saved. The rules below are the defaults those keys can change.

Implement one job at most, then stop for review. However much was approved, implement one job (one task, if the user asked for a task), hand back its review, and wait for the user to say go on before the next. Only the user lifts this, in words or with their review preference, and only as far as they say. Approval is the user saying so, in words, naming the task or its job — a silence, a thumbs-up on something else, or your own confidence that the fix is obvious are not approval.

Two things you may do without asking, because they are how the proposal gets written: read anything, and run read-only checks — greps, a throwaway probe in a scratch directory, a test suite that already exists. What you may not do is edit a file the fix would touch, or leave a scratch file behind in the repo.

If the task turns out to be wrong, say that instead of proposing a fix. A proposal that opens "this does not hold, here is why" is a good outcome and finishes the task — set the row to Refuted or By design with the evidence.

Legacy is the user's decision, not yours

There is no default. Do not assume the old path is removed, and do not assume it is kept. What the legacy logic is, what is lost without it, and which way you would go are asked in the question round, before the board is published, and the answer is on the task's row. Heading 7 states that answer. A task whose Legacy is undecided is not on this board.

Work in jobs, hand back a reviewable change

A job is a group of Queue tasks that share files or a seam and are implemented together. One lane per job, about five tasks or fewer; a High-risk or L-effort task is a job of its own. Before the proposals, give the job header: tasks, why together, files touched, order, effort · risk.

Every hunk belongs to exactly one task. After implementing, give the job review: what changed per task with file:line, the order to read it in, the proof per task, a git diff -- <files> per task, and what deliberately did not change.

PRs — every job lands in one, shown on the PRs tab

The PRs tab lists every PR with its shape: Independent (branches from the base and targets it, merge in any order) or Stacked (targets the PR below it, merge in order). A stack exists only because the user chose one. Before the first edit of any PR, check you are on its branch with a clean tree; if another PR's work is still uncommitted, stop and say so. In a stack, implement jobs in PR order.

When a PR's last job is reviewed, stacked or not, write its whole config on the PRs tab, the body included, and republish. The body never goes in chat; it lives here behind its Copy button. In chat, give the short fields, each in its own block (head branch, target branch, title, draft — yes unless every PR it builds on is merge-ready or the stack is complete, merge method, labels or reviewers only if the repo shows them), the next branch name, and a pointer to the body on this tab. You branch, commit, push or open the PR yourself only as the user's commit and push preferences allow, or when they say so, in words.

Stacks only: when the base moves, leave the stack alone unless the base probe shows a conflict, the repo requires up-to-date branches, or a PR landed by squash or rebase merge. Then sync by merging (or rebasing, only when the user asks), one PR at a time, bottom-up, each through the integration-assistant skill: a full run for the base into PR 1, then a propagation run per PR above it. Every link is verified (dry-run, clean-but-dangerous scan, the PR's suite and its job-review checks) and committed (by the user, unless their commit preference lets you) before the next starts. A PR in the middle that needs a new commit is synced first, then gets the commit, and only then does the sync go on to the PRs above it.

Issues — every task traces to one, or says where it came from

When tasks come from tracked issues, the Issues tab maps each issue to its tasks, jobs and PRs, and the Jobs and Queue tables carry an Issue column. A task with no issue is listed with its origin. Read issue states from the tracker, not memory. A PR body says Closes #n only when it finishes every remaining part of #n; otherwise Refs #n.

Stay in the cleared lane

Directories in the user's free lanes (saved per repo in ~/.claude/plan-build-board/lanes.md) are edited without asking. Every other directory a job reaches was asked in the question round, and the answer is on the task rows. Never edit outside the free lanes and what the answers cleared. Do not implement across the boundary because the fix is small — small is not the criterion.

Plan against the code, not against the row

Rows carry the evidence of the pass that wrote them, and the tree moves. Re-read the cited files before you write anything. Where what you find disagrees with the row, the code wins and the row gets corrected — that correction is part of the deliverable, not an aside.

Update the board in the same turn as the change

A status is only useful if it is true right now, so the row moves when the thing happens — not at the end of a batch and not "once it is all done". Every move updates three things together: the pill, the Evidence cell (what you did and what proved it), and the tally and chip counts in the header, which are hand-maintained and will silently disagree with the rows if you skip them.

The Queue is maintained too: a task that reaches Fixed leaves it and the ranks close up. If fixing one task changes another's priority, say so and re-rank rather than leaving a stale order behind.

Commits and pushes follow the user's preferences. By default work lands uncommitted: no commit, push or PR unless the preferences or the user's words allow it. Republish to the same URL so the link keeps working.
